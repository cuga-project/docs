# Manage, publish, and self-host

CUGA is not only a demo. You can edit an agent in the browser, try it safely as a **draft**, then **publish** a version that production chat uses — and you can run the same stack on a Kubernetes cluster.

## Manage and publish

```bash
cuga start manager
```

Open **http://localhost:7860**. You get a manage UI where you can:

- Add or edit tools, MCP servers, and OpenAPI apps
- Pick the LLM and advanced model parameters
- Attach [policies](/docs/sdk/policies) (including [ToolGuard](/docs/sdk/policies/tool-guard))
- Chat against the **draft** without changing what production users see
- **Publish** when the draft looks right — CUGA stores a versioned config so you can audit what shipped and roll forward

<Callout type="info">
Draft chat is for you. Published chat is for everyone else. Publish only when you are happy with the draft.
</Callout>

Typical loop:

<Steps>
<Step>
### Start manager

```bash
cuga start manager
```
</Step>
<Step>
### Edit the draft

Change tools, MCP, model, or policies. Try a few tasks in draft chat.
</Step>
<Step>
### Publish

Publish creates a new version. Production chat switches to that version.
</Step>
</Steps>

When `storage.mode = "prod"`, CUGA can keep existing published configs on startup instead of reseeding demo data. See [`preserve_configs_on_startup`](/docs/customization/settings-reference#storage).

## Other start presets

`cuga start` takes a **preset**. These are the ones you will use most:

| Command | What you get |
| --- | --- |
| `cuga start demo` | Default chat demo |
| `cuga start manager` | Manage UI + draft/publish |
| `cuga start demo_knowledge` | Demo with the knowledge engine on |
| `cuga start demo_skills` | Demo with agent skills and a sandbox |
| `cuga start demo_crm` | CRM + email sample apps |
| `cuga start demo_supervisor` | CRM demo with `CugaSupervisor` |
| `cuga start demo_health` | Healthcare OpenAPI sample (`cuga-oak-health`) |
| `cuga start demo_docs` | IBM Docs MCP sample |
| `cuga start travel_agent` | Multi-agent travel sample |
| `cuga start registry` | API registry only |
| `cuga start appworld` | AppWorld evaluation environment |

See [Control Commands](/docs/customization/cli-sdk) for the full CLI.

## Self-host on Kubernetes

The [cuga-agent](https://github.com/cuga-project/cuga-agent) repo ships a Helm chart and helper scripts.

<Steps>
<Step>
### Prerequisites

Helm 3 and a cluster (kind, minikube, Docker Desktop Kubernetes, or a cloud cluster such as GKE / EKS / AKS).
</Step>
<Step>
### Local cluster (kind / minikube)

From the `cuga-agent` repository root:

```bash
cp deployment/.env.example deployment/.env
# Set GROQ_API_KEY or OPENAI_API_KEY

./deployment/deploy-local.sh
kubectl port-forward svc/cuga 7860:7860
```

Open **http://localhost:7860**.
</Step>
<Step>
### Cloud cluster

Build and push the image to your registry, then install the chart under `deployment/helm/` with API keys as Kubernetes secrets. The full walkthrough lives in [`deployment/README.md`](https://github.com/cuga-project/cuga-agent/blob/main/deployment/README.md) in the agent repo.
</Step>
</Steps>

<Callout type="info">
This page stays short on purpose. Cluster-specific values (ingress, TLS, image pull secrets) change per environment — use the Helm README as the source of truth when you deploy.
</Callout>
